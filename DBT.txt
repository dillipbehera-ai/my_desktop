DBT Core Concepts



### ✅ 1. What is DBT?

DBT (Data Build Tool) is a command-line tool that enables data transformation within your data warehouse using SQL and Jinja. It focuses purely on the "T" in ELT.
It supports modular SQL code, version control (Git), testing, documentation, and CI/CD.
Each SQL file in the `models/` folder becomes a table or view in your warehouse.

**Example:**

```bash
dbt run --select stg_orders
```

---

### ✅ 2. What is an Incremental Model?✅✅✅✅

Incremental models allow DBT to insert only new or updated data instead of rebuilding the entire dataset.
Ideal for large tables (e.g., transactions, logs).
Uses the `{{ is_incremental() }}` function to apply conditional logic.
Requires a timestamp or unique ID to detect new records.
Improves performance and cost efficiency.

**Example:**

```sql
{% if is_incremental() %}
  WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }})
{% endif %}
```

---

### ✅ 3. What is a Snapshot?✅✅✅✅✅

Snapshots in DBT implement Slowly Changing Dimensions (SCD Type 2).
They track changes in row-level data over time.
Defined using YAML for configuration and SQL for business logic.
Uses either `timestamp` or `check` strategy to detect changes.
Useful for maintaining historical records for customer or employee data.

**Example:**

```yaml
strategy: timestamp
updated_at: updated_at_column
```

---

### ✅ 4. What is ref()?✅✅✅✅✅✅✅

`ref()` is used to reference other DBT models and handle dependency management.
Ensures proper build order and abstracts schema/database names.
Allows modular model design and automatic DAG generation.
Required for lineage tracking and CI/CD integration.
Always use `ref()` instead of hardcoding schema.table names.

**Example:**

```sql
SELECT * FROM {{ ref('stg_customers') }}
```

---

### ✅ 5. What is a Schema Test?✅✅✅✅✅✅✅✅

Schema tests ensure data quality rules like uniqueness or not null constraints.
Defined in `schema.yml` alongside the model definition.
Run with `dbt test` to detect data issues early.
Supports built-in and custom SQL tests.
Improves trust and reliability in data transformations.

**Example:**

```yaml
- name: customer_id
  tests:
    - not_null
    - unique
```

---

### ✅ 6. What is a Custom Test?✅✅✅✅✅✅✅✅✅

Custom tests let you define SQL queries to check for invalid data patterns.
They return rows that violate business rules.
Placed in the `tests/` folder or inline in YAML.
Help validate complex rules beyond built-in tests.
Used for fraud checks, invalid amounts, etc.

**Example:**

```sql
SELECT * FROM orders WHERE amount < 0
```

---

### ✅ 7. What is source()?✅✅✅✅✅✅✅

`source()` refers to raw/external tables that DBT doesn't create.
Used to document external dependencies and apply tests.
Defined in `sources:` block of a YAML file.
Helps track lineage from ingestion to transformation.
Useful for governance and debugging.

**Example:**

```sql
SELECT * FROM {{ source('raw', 'customers') }}
```

---

### ✅ 8. What is a Seed in DBT?✅✅✅✅✅✅✅

Seeds are CSV files in the `data/` folder that DBT loads as tables.
They help initialize small reference tables like countries or categories.
Run using `dbt seed` command.
They support version control and testing like any model.
Seeds are great for static lookup data.

**Example:**

```bash
dbt seed --select country_codes
```

---

### ✅ 9. What is a Macro in DBT?✅✅✅✅✅✅✅✅

Macros are reusable Jinja functions stored in `.sql` files under `macros/`.
They reduce repeated logic and support parameterization.
Can be used for dynamic SQL generation, logging, or conditional logic.
Called using `{{ macro_name(args) }}`.
Supports DRY principles in DBT projects.

**Example:**

```sql
{% macro default_zero(col) %} COALESCE({{ col }}, 0) {% endmacro %}
```

---

### ✅ 10. What is env\_var()?✅✅✅✅✅✅✅✅✅

`env_var()` is a Jinja function that pulls environment variables into DBT.
Used to inject secrets or parameters like API keys or schema names.
Avoids hardcoding sensitive values in SQL or YAML.
Used in `profiles.yml`, macros, or configs.
Secures credentials in CI/CD pipelines.

**Example:**

```sql
{{ env_var('DB_PASSWORD') }}
```

---

### ✅ 11. What is var()?✅✅✅✅✅✅✅✅✅✅
✅
`var()` accesses runtime variables defined in `dbt_project.yml` or CLI.
Useful for changing logic or behavior across environments.
Fallback defaults can be defined inline.
Accessible in SQL or Jinja templates.
Supports parameterization of models.

**Example:**

```sql
{{ var('run_date', '2024-01-01') }}
```

---

### ✅ 12. What is an Ephemeral Model?✅✅✅✅✅✅

Ephemeral models are temporary CTEs used inline in SQL logic.
They are not built in the warehouse as tables/views.
Useful for small transformations or intermediate steps.
Materialized only during dbt run execution.
Great for simplifying logic while avoiding clutter.

**Example:**

```sql
{{ config(materialized='ephemeral') }}
```

---

### ✅ 13. What is dbt build?✅✅✅✅✅✅✅✅

`dbt build` runs models, tests, snapshots, and seeds together.
It is an all-in-one command ideal for production pipelines.
Ensures that transformations and validations run in sync.
Reduces chance of partial/incomplete builds.
Preferred over running `dbt run` + `dbt test` separately.

**Example:**

```bash
dbt build --select dim_customers+
```

---

### ✅ 14. What is dbt run?✅✅✅✅✅✅✅✅

`dbt run` compiles and executes all models (SQL files) into tables/views.
You can select specific models using flags.
Runs only transformations, not tests or seeds.
Supports incremental builds, partitioning, and dependency resolution.
Most commonly used dbt command.

**Example:**

```bash
dbt run --select stg_orders+
```

---

### ✅ 15. How to Schedule DBT?✅✅✅✅✅✅✅✅

Use DBT Cloud’s UI scheduler or integrate with Airflow/GitHub Actions.
Jobs can run hourly/daily or on-demand.
DBT Cloud supports job monitoring, retry logic, and notifications.
Custom schedulers use `dbt run` or `dbt build` as shell commands.
Enable production automation.

**Example:**

```yaml
on:
  schedule:
    - cron: '0 1 * * *'  # daily at 1am
```

---

### ✅ 16. What is a DAG in DBT?✅✅✅✅✅✅✅

DAG (Directed Acyclic Graph) shows dependency flow among models.
Created automatically via `ref()` usage.
Visible in DBT Cloud UI or via `dbt docs generate`.
Ensures correct model execution order.
Improves maintainability and debugging.

**Example:**

```bash
dbt docs generate && dbt docs serve
```

---

### ✅ 17. What is dbt test?✅✅✅✅✅✅✅

Runs schema and custom data quality tests.
Helps validate assumptions about data (e.g., uniqueness, nulls).
Output is shown in terminal or saved to `target/run_results.json`.
Tests fail jobs in CI pipelines.
Improves trust in analytics workflows.

**Example:**

```bash
dbt test --select customers
```

---

### ✅ 18. How to rollback a model?✅✅✅✅

Use Git to revert changes and re-run `dbt run`.
Snowflake users can also query older versions via Time Travel.
Ensure snapshot/backup if data loss is critical.
Use `dbt build` to validate changes before production.
Combine with CI/CD to prevent bad merges.

**Example:**

```bash
git checkout HEAD~1 -- models/customer.sql
```

---

### ✅ 19. How to loop with Jinja?✅✅✅✅✅✅✅

Jinja supports for-loops for dynamic SQL generation.
Used in macros or model logic to repeat structures.
Ideal for unioning monthly partitions or dynamic pivots.
Avoids repetitive code blocks.
Powerful for dynamic logic in dbt.

**Example:**

```sql
{% for month in ['Jan', 'Feb'] %}
SELECT '{{ month }}' as month
{% endfor %}
```

---

### ✅ 20. How to log in DBT?

Use the `log()` macro in Jinja to output messages to console/logs.
Helpful for debugging and status reporting in macros/models.
Log level can be `info`, `warn`, or `debug`.
Visible in DBT Cloud job output or local run.
Add checkpoints or metadata tracking.

**Example:**

```sql
{{ log('Starting model transformation', info=True) }}
```

✅ What is DBT?
DBT is a SQL-based tool for transforming data in the warehouse using modular SQL + version control.
E.g., dbt run creates a transformed table from raw data.

✅ How is DBT different from ETL tools like Glue?
DBT only handles the T (transform); it assumes data is already in the warehouse.
Use Glue to load → DBT to transform.

✅ What is a DBT model?
A .sql file that becomes a table or view after dbt run.
E.g., models/orders.sql.

✅ What is a source in DBT?
Reference to external/raw tables not created by DBT.
E.g., source('raw', 'customers').

✅ What is materialization?
Controls how DBT builds models: table, view, incremental, ephemeral.
E.g., {{ config(materialized='table') }}.

🔹 Incremental & Dependencies
✅ What is an incremental model?
Only processes new or changed data since last run.

Use is_incremental() in SQL.

✅ How to define incremental logic?


WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }})

✅ What is ref()?
Connects DBT models for dependency management.
E.g., ref('stg_orders').

✅ What is source()?
Used to refer to raw/external tables in DBT.
E.g., source('raw', 'orders').

✅ Difference between ref() and source()?
ref() is for DBT models; source() is for raw tables.
Both help track lineage.

Test that customer_id is not null.

✅ What are DBT snapshots?
Track historical changes (SCD Type 2).
Useful for customer dimension tracking.

✅ How to define a snapshot?
Use a .sql in snapshots/ with timestamp strategy.
E.g., strategy: timestamp.

✅ When to use snapshots vs incrementals?
Snapshots for full history; incremental for recent changes only.

Templating engine for logic in SQL.
